# Otto 통합 검증

## 왜 "경계"를 보는가

펌웨어만 보면 컴파일이 되고, 웹만 보면 버튼이 눌린다. 실제 결함은 둘이 만나는 곳에 숨어 있다: 웹이 보낸 인자 수를 펌웨어가 다르게 셈, 웹은 ACK를 1.5초 기다리는데 펌웨어는 동작이 끝난 3초 뒤에 ACK, 펌웨어는 FALLEN 중 ERR를 보내는데 웹은 무시. 그래서 파일 존재 확인이 아니라 **양쪽 코드를 나란히 놓고 대조**한다.

## 1. 자동 검사 (항상 먼저, 이 순서로)

```bash
python .claude/skills/otto-protocol/scripts/gen_protocol.py --root . --check
python .claude/skills/otto-protocol/scripts/check_contract.py --root .
node   .claude/skills/otto-protocol/scripts/test_protocol_js.mjs .
python .claude/skills/otto-firmware/scripts/compile.py --sketch firmware/otto_fat --log _workspace/qa_compile.log
node --check web/js/*.js        # 각 파일 문법 검사 (파일마다 실행)
```

하나라도 실패하면 결과를 그대로 보고서에 붙인다. 실패 원인을 추측으로 고쳐 적지 않는다.

## 2. 경계 대조 체크리스트 (코드를 읽어서 확인)

**명령 처리 경로 (펌웨어)**
- [ ] 줄 버퍼가 `PROTO_MAX_LINE`을 넘으면 `ERR LINE_TOO_LONG`을 보내고 줄 끝까지 버린다(다음 줄이 깨지지 않는다).
- [ ] 인자 개수가 `*_MIN_ARGC` 미만·`*_ARGC` 초과, 범위 밖이면 `ERR BAD_ARG`이고 **아무 동작도 하지 않는다**.
- [ ] 생략된 인자에 `*_DEFAULT`를 쓴다.
- [ ] ACK는 검증 직후, 블로킹 동작 **이전**에 보낸다. DONE은 실행 후.
- [ ] 음수 인자(TRIM)를 올바르게 파싱한다(`atoi`/`strtol` 부호).
- [ ] TEXT의 str 인자는 토큰 뒤 공백 이후 줄 끝까지 전체다(공백 포함).
- [ ] 프로토콜 번호(제스처·노래·입모양·동작)를 Otto 라이브러리 상수로 **변환**한다. 노래는 순서가 달라 표가 필요하고 제스처는 0부터다(`otto-hardware/references/otto-lib-api.md`). 헤더(`Otto_gestures.h`, `Otto_sounds.h`)의 실제 값과 대조한다.
- [ ] USB와 BT 두 입력이 각자의 버퍼를 갖고, 응답이 명령을 보낸 쪽으로 간다.
- [ ] STOP은 연속 MOVE 주기 사이에서 처리되고, FALLEN 상태에서도 받는다.

**웹 쪽**
- [ ] 모든 송신이 `encode()`를 거친다(계약 검사 경고 확인).
- [ ] ACK 타임아웃(웹) > 펌웨어가 ACK를 보내기까지 걸리는 최악 시간. 1회성 동작 완료 대기는 DONE 기준이며, 그 타임아웃은 가장 긴 제스처/노래(수 초)보다 길다.
- [ ] ERR 코드가 사용자에게 의미 있는 한국어 메시지로 표시된다(`ERR_NAME` 사용).
- [ ] EVENT 6종, STATE 5종이 화면에 반영된다.
- [ ] 수신 줄이 조각나 와도(예: `"t 23 0 "` + `"1 -2 40 0\n"`) 정상 처리된다.
- [ ] 연결 해제·케이블 뽑힘 후 UI가 멈추지 않고 재연결할 수 있다.
- [ ] 데모 로봇이 실제 펌웨어와 같은 규칙(ACK 시점, ERR 조건)을 따른다 — 다르면 데모에서 통과한 것이 실물에서 실패한다.

**안전·하드웨어**
- [ ] 자동 반응 우선순위: 넘어짐 > 터치 > 장애물 > 명령.
- [ ] 장애물 후퇴는 전진 중에만, 히스테리시스 있음. 이벤트가 반복 폭주하지 않는다.
- [ ] 넘어지면 서보 detach, 회복 시 attach.
- [ ] `Wire.setWireTimeout` 사용, IMU 실패 시 펌웨어가 멈추지 않는다.
- [ ] `pulseIn` 타임아웃 ≤ 25ms.
- [ ] `String` 클래스 미사용, 상수 문자열 `F()`.
- [ ] 핀 번호가 `otto-hardware`의 핀 표와 일치한다.

## 3. 판정과 보고

보고서: `_workspace/{phase}_qa_report.md`

```markdown
# QA 보고 — {날짜} {대상: firmware|web|통합}
## 자동 검사
| 검사 | 결과 | 요약 |
## 결함 (심각도순)
### [치명|주요|경미] 제목
- 위치: 파일:줄
- 근거: 양쪽 코드 인용 또는 검사 출력
- 영향: 사용자가 겪는 증상
- 수정 제안: 담당(firmware|web|protocol)과 구체적 방향
## 하드웨어에서만 확인 가능한 항목
## 통과 판정: PASS | FAIL (치명·주요 0건이어야 PASS)
```

- **치명**: 컴파일 실패, 계약 오류, 안전 반응 불능, 로봇이 멈추거나 서보가 범위 밖으로 감
- **주요**: 기능 하나가 동작하지 않음, 메모리 한도 초과, 오류가 사용자에게 안 보임
- **경미**: 표시·문구·경고

결함마다 담당을 정해야 오케스트레이터가 해당 에이전트에게만 전달할 수 있다. 프로토콜 정의 자체의 문제면 담당은 `protocol`이다.

## 4. 하드웨어 시험 문서

통합 PASS 후 `docs/hardware-test.md`를 만들거나 갱신한다. 사용자가 로봇 앞에서 순서대로 따라 할 수 있게, 항목마다 "할 일 → 기대 결과 → 다르면 바꿀 곳(config.h 상수 이름)"을 적는다. 최소 항목: 업로드, 부팅 진단 문자열, 시리얼 모니터로 `P` 입력, 웹에서 BLE 'otto2' 선택·연결, 20바이트 넘는 명령(MATRIX) 전송, 각 서보 방향과 팔 좌우, 트림, 매트릭스 방향, 터치, 초음파 거리, 기울기 축·부호, 넘어짐 감지, 장애물 후퇴, 전원(서보 동시 구동 시 리셋 여부).
